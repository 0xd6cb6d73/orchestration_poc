# hybrid_v2.1 SQL strategy

`hybrid_v2_1` is a separate SQL benchmark strategy. `hybrid_v2` keeps its existing
behavior and reports. The new adapter is available in native and JSON forms as
`hybrid_v2_1` and `hybrid_v2_1-json`.

## Execution contract

1. The orchestrator proposes a structurally valid dependency plan. Every task names
   its allowed public SQL tables, `TaskEvidence` output schema, and positive limits
   for requests, SQL calls, tokens, and seconds. A plan judge can abstain on
   feasibility when the plan needs investigation; an explicitly unsupported or
   structurally invalid plan is rejected. Plan selection still uses the existing
   deterministic collaboration controller.
2. The scheduler executes a dependency wave and audits its outputs before running
   the next wave. A dependent task requires viable prerequisite artifacts. When a
   task is revised, the scheduler invalidates all descendants and reruns them only
   after their prerequisites pass again. Accepted prerequisite outputs are included
   in the dependent worker input. Decisions may revise only the pending task.
3. A task worker can query only the tables named in its plan contract. SQLite's
   authorizer denies reads from other tables. The worker returns proposed values,
   evidence-backed findings, assumptions, and unresolved questions. Each asserted
   finding must cite a query reference generated by that worker. The scoped goal
   contract is recorded before execution, and task limits cover retries within
   one execution attempt. The task pool is divided using the selected plan size
   plus the bounded decision rounds, so small plans retain useful SQL capacity.
4. Integration returns final values with a `supported`, `partial`, or
   `inconclusive` status, evidence-backed claims, assumptions, and unresolved
   questions. A partial or inconclusive result must disclose a gap. A supported
   result requires accepted coverage of every planned task and the public answer
   shape contract; partial values may cover
   only a subset of public identifiers but retain their required value types.
   An independent verifier checks claims and gap disclosure; task, integration,
   and verifier query references are persisted in the verification verdict before
   the completion gate.

The table allowlist is a mechanical SQL boundary. Free-text `local_scope`,
`out_of_scope`, and definitions of done still require model judgment for their
semantic meaning. Evidence references prove that a query occurred; the task
critic and independent verifier assess whether the query supports the claim.

Prerequisite outputs are currently embedded in dependent prompts. Large outputs
may still hit context admission; artifact-reference payloads remain a separate
follow-up.

This version currently covers the SQL benchmark adapter. The live reporting
runtime still uses its existing `hybrid_v2` workflow; its decision validator now
binds revisions to the pending task. The v2.1 variant has deterministic tests and
infrastructure diagnostics, but no new paid model benchmark result yet.
